# 습관 잔디 코드 리뷰

이 프로젝트는 `index.html` 한 파일에 HTML·CSS·JS가 모두 들어 있는 정적 웹앱이다. 서버 없이 브라우저 localStorage에만 기록을 저장하므로, 버그 하나가 곧 사용자의 기록 유실로 이어진다. 리뷰의 목적은 취향 지적이 아니라 **사용자가 실제로 겪을 문제를 커밋 전에 찾는 것**이다.

## 1. 리뷰 범위 정하기

- 사용자가 파일·함수·변경을 지정했으면 그것만 본다.
- 지정이 없으면 git 상태로 정한다.
  - `git diff HEAD`(커밋되지 않은 변경)와 `git status --short`(새 파일)를 본다.
  - 커밋이 하나도 없거나 변경이 없으면 `index.html` 전체를 리뷰한다.
- 무엇을 리뷰했는지 보고서 첫 줄에 적는다. 범위가 적혀 있지 않으면 읽는 사람이 무엇을 확인받았는지 알 수 없다.

## 2. 읽기

변경된 줄만 보지 말고, 그 함수를 호출하는 쪽과 그 함수가 쓰는 상태까지 따라가서 읽는다. 이 앱은 `habits`, `today`, `storageOk`, `editingId` 같은 전역 상태를 여러 함수가 공유하므로, 한 곳의 변경이 다른 함수의 가정을 깨는 경우가 많다. `index.html`은 700줄 남짓이라 필요하면 전체를 읽어도 된다.

## 3. 체크리스트

아래는 이 코드베이스가 이미 지키고 있는 규칙이다. 변경이 이 규칙을 깨는지를 중심으로 본다. 체크리스트에 없는 문제(로직 오류, 경계값, 이벤트 중복 등록 등)도 당연히 찾는다. 체크리스트는 시작점일 뿐이다.

### 날짜 (가장 깨지기 쉬움)
- 날짜 키(`YYYY-MM-DD`)는 `toKey` / `parseKey` / `addDays`로만 만든다. `toISOString()`은 UTC 기준이라 한국 시간 오전 9시 이전에는 어제 날짜가 나온다. (`exportedAt`처럼 시각을 기록하는 용도는 예외)
- `key > today` 같은 문자열 비교는 0으로 채운 고정 길이 형식이라서 성립한다. 키 형식을 바꾸는 변경은 이 비교들을 모두 깨뜨린다.
- `today`는 캐시된 값이다. 탭을 연 채 자정이 지나면 낡은 값이 되므로, 기록을 바꾸는 동작은 `toggle`처럼 `todayKey() !== today`를 먼저 확인해야 한다.
- 날짜는 `new Date(y, m, d + n)`처럼 날짜 단위로 더한다. 밀리초(`86400000`)를 더하면 서머타임이 있는 지역에서 하루가 어긋난다.
- streak 계산은 오늘 미체크 시 어제부터 세는 규칙, 월·연 경계, 체크가 하나도 없는 경우를 확인한다.

### 데이터 보존
- `localStorage` 접근은 전부 `try/catch`로 감싼다. 시크릿 창, 저장소 차단, 용량 초과에서 예외가 난다. 실패하면 `storageOk = false`가 되어 경고 배너가 떠야 한다.
- 저장소나 가져온 파일처럼 외부에서 들어온 데이터는 반드시 `normalize()`를 거친다. 습관에 새 필드를 추가했다면 `normalize`에도 검증과 기본값이 추가됐는지 확인한다. 빠지면 저장은 되는데 다시 불러올 때 사라지거나, 기존 사용자 데이터에서 `undefined`가 된다.
- 가져오기는 형식이 틀리면 기존 데이터를 건드리지 않고, 덮어쓰기 전에 `confirm`을 받는다.
- 저장 형식이 바뀌면 `version` 값과 기존 데이터를 읽는 방법도 함께 바뀌어야 한다.

### 보안 (XSS)
- 습관 이름·이모지·가져온 JSON은 모두 사용자 입력이다. `textContent`, `setAttribute`, `dataset`으로만 DOM에 넣는다. `innerHTML`, `insertAdjacentHTML`, `outerHTML`에 이 값이 섞이면 🔴다. 가져오기 기능 때문에 남이 만든 JSON이 들어올 수 있다.
- `querySelector` 선택자 문자열에 값을 끼워 넣을 때는 그 값이 앱이 만든 값(예: 검증된 날짜 키)인지 확인한다.

### 접근성
- 아이콘만 있는 버튼은 `aria-label`, 켜짐/꺼짐 버튼은 `aria-pressed`를 상태와 함께 갱신한다.
- 카드를 다시 그리면 포커스가 사라진다. `toggle`의 `focusSelector`처럼 포커스를 원래 요소로 돌려놓는지 본다.
- 마우스 없이 키보드만으로 추가·체크·수정·삭제·모달 닫기가 모두 되는지 본다.
- 습관 색은 두 테마의 빈 칸 색과 3:1 이상 대비가 나와야 한다(`COLORS` 위 주석). 색을 추가·변경하면 확인한다.

### 테마와 레이아웃
- 색은 `:root`의 CSS 변수로만 쓴다. 다크 테마 값은 `@media (prefers-color-scheme: dark)` 블록과 `:root[data-theme="dark"]` 블록 **두 곳**에 있다. 한쪽만 고치면 "시스템 다크"와 "직접 고른 다크"가 다르게 보인다.
- 360px 폭에서 가로 스크롤이 생기지 않아야 한다. 히트맵 칸 크기는 `--cell`의 `clamp()`에 의존한다.

### 코드 일관성
- 이미 있는 유틸(`$`, `toKey`, `addDays`, `firstGrapheme`, `newId` 등)을 다시 만들지 않았는지 본다.
- 주석은 "무엇"이 아니라 "왜"를 한국어로 쓰는 것이 이 파일의 관례다. 섹션은 `// ---- 이름`으로 나눈다.
- 외부 라이브러리 없이 파일 하나로 동작하는 구조를 유지한다.

## 4. 보고하기 전에 검증하기

발견마다 스스로 묻는다: **"어떤 입력과 상황에서 사용자가 무엇을 보게 되는가?"** 이걸 구체적으로 쓸 수 없으면 아직 확인이 덜 된 것이다. 코드를 다시 읽어 실제 실행 경로를 따라가 본다.

- 재현 시나리오가 성립하면 보고한다.
- 다른 곳에서 이미 막혀 있으면 버린다. (예: 이름 길이는 입력창의 `maxlength="30"`과 `normalize`의 `slice(0, 30)`이 함께 막고 있다)
- 확신이 없으면 "확인 필요"로 낮추고 이유를 적는다.

공백·따옴표·세미콜론처럼 포매터나 린터가 잡을 지적은 하지 않는다. 발견이 없으면 억지로 만들지 말고 "문제 없음"이라고 쓴다. 잡음이 많은 리뷰는 진짜 문제를 묻어 버린다.

## 5. 보고 형식

파일은 수정하지 않는다. 수정 방법은 제안으로만 적고, 고칠지는 사용자가 정한다.

```markdown
## 코드 리뷰: <리뷰 대상 — 예: index.html 전체 / 커밋되지 않은 변경>

<한두 문장 총평: 커밋해도 되는지, 가장 중요한 문제가 무엇인지>

### 🔴 반드시 수정
1. **<문제를 한 줄로>** — `index.html:123`
   - 상황: <어떤 입력·순서에서>
   - 결과: <사용자가 겪는 일 — 기록 유실, 잘못된 날짜 표시 등>
   - 제안: <고치는 방법, 필요하면 짧은 코드>

### 🟡 수정 권장
(같은 형식)

### 🟢 참고
(한 줄씩, 선택 사항)

### 확인한 항목
날짜 ✅ · 데이터 보존 ✅ · XSS ✅ · 접근성 ⚠️ 1건 · 테마/레이아웃 ✅ · 일관성 ✅
```

심각도 기준:
- 🔴 반드시 수정: 기록 유실·손상, XSS, 특정 날짜·시간대에 틀린 결과, 핵심 기능(추가·체크·저장·가져오기)이 동작하지 않음
- 🟡 수정 권장: 드문 조건에서만 나는 버그, 키보드·스크린리더 사용자가 막히는 문제, 기존 규칙과 어긋나서 다음 변경 때 버그가 될 코드
- 🟢 참고: 더 단순하게 쓸 수 있는 코드, 사소한 일관성 문제
